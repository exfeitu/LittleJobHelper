# AI 辅助开发：从 Context 到 Harness

本文档记录本项目的 AI 开发方法论，以及从实践中总结的正确流程。

---

## 一、核心理念：Context → Harness

用 AI 写代码和请人写代码有本质区别：

| | 请人写 | 请 AI 写 |
|---|---|---|
| 记忆 | 有上下文，记得昨天的讨论 | 每次对话从零开始 |
| 理解 | 能揣摩意图 | 只能按字面执行 |
| 犯错 | 会主动检查 | 不会质疑自己的输出 |
| 速度 | 慢 | 快 |

因此，AI 开发的核心不是"写代码快"，而是 **"让 AI 少犯错"**。

**Context（上下文）** 是让 AI 知道项目是什么。
**Harness（约束系统）** 是让 AI 不能做错事。

你从 `AGENTS.md` 的 4 次迭代中，已经完成了这个进化：

```
v1: 搭个架子，下一步先部署上线        → 没有 AI 文件
v2: 更新AI开发context文件              → 有 Context，AI 知道项目结构
v3: 重新构建ai context                → 10 条禁止事项，AI 被约束
v4: 基本完善（当前）                    → 7 个变更模式，AI 按套路出牌
```

## 二、项目生命周期四阶段

### 阶段 1：初始化（第 1-2 次对话）

**目标**：跑起来 + 部署上线

**你需要做的**：
1. 明确技术栈选型（Next.js 静态导出 + GitHub Pages + LocalStorage）
2. 让 AI 生成项目脚手架
3. 配置 CI/CD（GitHub Actions deploy.yml）
4. 验证 `npm run build` 通过，线上可访问

**交付物**：
- 可运行的空项目
- 自动部署流水线
- 初始 `AGENTS.md`（哪怕只有 10 行）

**本项目的教训**：
- CI 配置改了 5 次才稳定（分支名、Node 版本、basePath），这类问题应该让 AI 一次性给全方案，而不是改一点试一次

---

### 阶段 2：搭骨架（第 3-5 次对话）

**目标**：数据模型 + 核心组件 + 数据流

**你需要做的**：
1. 定义数据类型（`types.ts`）——这是最重要的决策，改类型成本极高
2. 实现数据流（加载 → 渲染 → 保存）
3. 搭建核心 UI 组件（不是美化，是功能）

**AGENTS.md 内容**：
- 目录结构
- 数据流图
- 组件 Props 约定
- 禁止事项（技术栈限制）

**本项目的教训**：
- `types.ts` 只改了 1 次（加 `updatedAt`），说明数据模型设计得不错
- 数据流用 `isInitialized` 守卫避免 LocalStorage 覆盖，这个模式来自 AI 的建议，非常正确

---

### 阶段 3：迭代功能（主要工作量）

**目标**：一个接一个地加功能

**正确的流程**（每个功能循此环）：

```
1. 写需求（1 句话 + 验收条件）
2. AI 出方案（改哪些文件，什么策略）
3. 你审核方案（别让 AI 直接写代码）
4. AI 写代码
5. npm run build（编译通过）
6. 浏览器验证（功能正确）
7. 提交 git（原子化，一个功能一个提交）
```

**错误流程**（本项目犯过的）：

```
1. 丢一句话给 AI
2. AI 写代码
3. 你说"不太对，改成 X"
4. AI 改
5. 你说"还有 Y 不对"
6. 来回 5-7 轮
7. 勉强能用，但代码质量下降
```

**关键区别**：**第 3 步"审核方案"是最省时间的**。花 2 分钟读方案能省 20 分钟的来回修改。

**本项目的典型案例**：

| 功能 | 循环次数 | 问题 |
|---|---|---|
| 缩放优化 | 7+ 轮 | 每轮解决一个瓶颈，缺乏整体性能分析 |
| 标题大小 | 1 轮 | 需求明确 |
| 云同步 | 2 轮 | 方案清晰，只是细节调整 |
| 标签管理 | 1 轮 | 第一次用弹窗，你说要内联，立刻改 |

---

### 阶段 4：收敛完善

**目标**：性能、重构、文档

**你需要做的**：
1. 性能优化（Chrome DevTools → Performance 面板）
2. 代码重构（消除重复，拆大文件）
3. 文档更新（AGENTS.md 与代码同步）

**本项目的当前状态**：刚完成 `useAppData` hook 提取，消除了 page.tsx 和 calendar 的重复代码。

## 三、和 AI 对话的 5 条铁律

### 1. 先给方案，再写代码

❌ "帮我优化缩放性能"
✅ "缩放不丝滑。先分析瓶颈在哪，告诉我你的方案，我确认后再改代码"

### 2. 性能问题给数据，不要给感觉

❌ "缩放还是不丝滑"
✅ "缩放时 DevTools Performance 显示 Rendering 占 40%，Painting 占 50%。附截图"

### 3. 一个消息一个主题

❌ "缩放不丝滑 + 标题太小 + 搜索有问题 + 帮我加个按钮"
✅ 拆成 4 条独立消息，每次只做一件事

### 4. 验收条件要明确

❌ "改好就行"
✅ "`npm run build` 零错误，页面刷新后滚轮能缩放，缩放范围 1h~30d"

### 5. git 提交要原子化

每个功能改完就提交，不要堆一堆修改再 `基本完善`。

```
✅ 好的提交历史：
  feat: 添加标签管理功能
  fix: 缩放 RAF 批处理防止抖动
  refactor: 提取 useAppData hook

❌ 坏的提交历史：
  基本完善（改了 10 个文件，啥都有）
```

## 四、AGENTS.md 的正确写法

### 必须有的内容

```markdown
## 技术栈（有哪些 + 明确没有哪些）
## 目录结构（每个文件一句话）
## 数据流（从加载到渲染到保存的完整链路）
## 禁止事项（AI 不能做的事）
## 常见变更模式（加字段、加组件、加页面的标准操作）
```

### 加分项

```markdown
## 设计决策记录（ADR）
  为什么 max zoom 是 24 而不是 1？
  为什么用 transform 而不是 left？

## 已知问题
  时间轴在 500+ 条目时会卡（暂未解决）
  搜索不支持拼音

## 测试策略
  当前：npm run build + 人工验证
  计划：Playwright smoke test
```

### 不要写的内容

```markdown
❌ 每个函数的具体实现（代码会变，文档会过期）
❌ "可能"、"应该" 等模糊词
❌ 过长的历史记录（git log 已经有了）
```

## 五、质量保障的最低标准

### 当前有

- `npm run build`（编译 + 类型检查）
- 人工浏览器验证

### 建议增加（按优先级）

1. **类型安全**：已经有 TypeScript strict mode，继续保持
2. **构建检查**：`npm run build` 必须在每次修改后通过
3. **数据迁移测试**：写一个脚本验证 v0→v1→v2 迁移正确
4. **Lint 规则**：加 `eslint-plugin-react-hooks` 防止 hooks 顺序错误
5. **Smoke Test**：用 Playwright 录一个"打开→添加任务→搜索→删除"的脚本
